## Goal

`claude-mods` is the one kit for starting work on new and existing projects. It must not depend on one model, one operating system or one agent harness. It holds:

- pinned third-party skills (from `mattpocock/skills`), copied unmodified,
- the three TOGAF-lite playbooks,
- scripts that install the skills, check a machine, and prepare a project.

pstack is a separate plugin. It is not copied into this repo, and no machine or project has to use it.

## Decisions (user, 2026-11-07)

2. ~~Supported: macOS and WSL only.~~ Replaced by decision 5.

What decisions 4 and 5 mean for the work (the agent's reading, change on request):

- **OS.** Scripts are bash and work on macOS, Linux and WSL. Native Windows is reached through Git Bash. The kit adds no new PowerShell script. The old `install-mods.ps1` stays. The Windows path is "verified by reading" until a person runs it.
- **Harness.** Skills and playbooks are plain Markdown. The script installs skills for Claude Code (`~/.claude/skills`) and for the shared `~/.agents/skills` folder that Codex, OpenCode and Gemini CLI read (today the `--codex` option). A harness-neutral name for that option is part of T5. Mods stay Claude Code only, because they use Claude Code calls.
- **LLM.** No kit script, playbook or doc may name a model. A vendored skill or a playbook that names a Claude tool (for example the Skill tool) is recorded as harness-specific in the manifest. Vendored files are not edited.
- **pstack.** pstack is optional. Playbooks use pstack's file format (`.agents/playbooks/`), so they load only where pstack is installed. Elsewhere they are plain Markdown for a person or agent to read.

## Defaults picked by the agent (change on request)

- Vendored skills go in `vendor/mattpocock-skills/<name>/`. Own skills stay in `skills/`. `install-skills.sh` reads both. A name clash between the two is an error.
- Playbooks live in `playbooks/` in this repo. A script copies them into a project's `.agents/playbooks/`. It copies, because committed symlinks break on some checkouts.
- The pin is one commit SHA of `mattpocock/skills`, in `vendor/MANIFEST.md`.
- Use the current upstream names: `to-spec` (was `to-prd`), `to-tickets` (was `to-issues`), `writing-great-skills` (was `write-a-skill`). Task T1 confirms them against the clone before anything is copied.
- Do not vendor Pocock's `tdd`. pstack has its own, and the playbooks say to use one.
- On WSL, clone this repo into the Linux file system (`~/`), not `/mnt/c`. WSL has its own `~/.claude`, separate from Windows.
- pstack needs 0.9.57 or later for project playbooks. This is a minimum, not a pin (user decision 4). pstack is installed per project with an explicit scope (`local`, `project` or `user`). Neither script picks a scope for the user.
- `doctor.sh` and `bootstrap-project.sh` do not read plugin files by path (such as `~/.claude/plugins/...`). They ask the `claude plugin` commands, and skip the pstack checks when `claude` is not installed.

## Order and parallel work

T1 first. Then T2 and T3 can run in parallel (separate files). T4 and T5 follow, also in parallel. T6 and T7 come last. T1 to T5 are small, so one agent can do them in order if the user prefers.

## Risks

- The upstream repo may have renamed or moved a skill since the lock file was written. T1 reports it and stops for that skill.
- A vendored `SKILL.md` that publishes to a tracker (`to-spec`, `to-tickets`) is safe only because the playbooks require human approval first. T1 records this.
- Until the pstack update (T8), T2 and T5 cannot be fully verified on this Mac.
